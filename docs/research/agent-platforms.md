# agent platforms: instruction files and pre-warm hooks

research date: 2026-11-26. Sources are public product docs only, and products
change fast; re-verify these pages before relying on a row. The rco pack
savings are unmeasured; card 1313 is the measurement.

This note is for the rco adoption guide (card 1313): which instruction
files a platform actually loads at session start, and where a pre-warm
or setup step could run `rco update` so a fresh VM starts with a warm
`rco.db`. A compact architecture comparison follows, with mill / grok
bot detail limited to what an outside reader needs.

flag. Copies in a subdirectory apply when work is in that tree.

**rco template implication (not a claim of measured savings):** the most portable committed file is root `AGENTS.md`. Repos that already use `CLAUDE.md` must also point or import from it, or claude code will ignore `AGENTS.md`. The gemini CLI needs `GEMINI.md` or a `context.fileName` setting, and aider needs an explicit `read:` entry. Copilot should get a line in `.github/copilot-instructions.md` when that file already exists.

## 2. pre-warm / setup steps where `rco update` could run

Goal: a warm `.rco/rco.db` (and/or a committed or generated pack) already on disk **before** the agent explores the tree. Each cloud VM is isolated; there is no shared live SQLite across agents. A snapshot is only as fresh as the last successful build.

| product | pre-warm / setup hook | good place for `rco update`? | freshness / caveats |
|---|---|---|---|
| **cursor cloud agents** | `.cursor/environment.json` (or a saved environment). The `install` script runs when cursor creates a **Build**; disk state is snapshotted; new agents start from the active Build. `start` / `terminals` run at agent boot, not at Build time. Self-hosted machines do **not** read `environment.json`. [setup](https://cursor.com/docs/cloud-agent/setup), [security](https://cursor.com/docs/cloud-agent/security) | **yes, in `install`.** This is the documented analog of "warm the cache ahead of the agent." | Build can lag `main` until it reruns. `install` must be idempotent. Failed builds do not replace the active Build. Agents do not share a VM or SQLite file. |
| **claude code cloud / scheduled tasks** | **setup script** on the cloud environment: runs as root **before claude code launches**. If it finishes in roughly **five minutes**, the filesystem is cached and later sessions skip the script (cache rebuilds when the script or network allowlist changes, or after roughly **seven days**). **SessionStart hooks** run after claude code launches, on every session (including resume), and are the documented place for project setup such as `npm install`. User-level hooks do not run in the cloud. [cloud environments](https://code.claude.com/docs/en/cloud-environments) | **yes, the setup script** (on-disk `rco.db` in the cached snapshot). A SessionStart hook can also run `rco update` every session (fresher, pays setup each time, after the process launches). | scripts over ~5 minutes are not cached. GitHub action runs are CI jobs, not this cache; `rco update` would belong in the workflow steps (per-job unless the workflow uses Actions cache, which is **unconfirmed** as a documented pattern). |
| **openai codex cloud** | A published **environment** includes repositories plus an **install script**. The product inspects the repo, installs dependencies, tests the workflow, then you publish. Each task gets its own isolated workspace; the published setup is reused. Saved VM state is recoverable up to **7 days** after the last turn or resume (this is VM state, not conversation retention). [cloud environments](https://learn.chatgpt.com/docs/environments/cloud-environments), [using codex cloud](https://help.openai.com/en/articles/20001545-using-codex-cloud) | **yes, the environment install script.** | Updates to a published environment apply to **new** tasks only. Exact install-script field name in the current UI vs legacy is easy to confuse; use the current "install script" docs. |
| **devin** | environment **snapshot**: a frozen bootable image (repos, tools, dependencies). Every session boots a fresh copy; session changes do not write back. A new snapshot is built when configuration changes. [environment setup](https://docs.devin.ai/onboard-devin/environment) | **yes, the blueprint / snapshot build.** | Same staleness issue as cursor builds. The cloning/setup time is documented as **not** consuming usage; agent work and VM time do. |
| **GitHub Copilot cloud agent** | sessions run in a cloud sandbox, on **GitHub Actions**, or a custom environment. For Actions, `.github/workflows/copilot-setup-steps.yml` (job name `copilot-setup-steps`, present on the default branch) runs **before Copilot starts**. This file does **not** apply to cloud-sandbox sessions. [customize the agent environment](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/customize-cloud-agent/customize-the-agent-environment) | **yes, for Actions-backed sessions**: add `rco update` as a setup step. **unconfirmed** for the default cloud sandbox (no setup-steps file). | This is per-session setup, not a cursor-style Build snapshot, unless the workflow also uses Actions cache (**unconfirmed**). |
| **google jules** | Per-repo **initial setup** script. "Run and snapshot" builds a snapshot reused for later tasks from that repository. For simple repos jules may infer setup from the repo, `AGENTS.md`, or `README.md`. [environment setup](https://jules.google/docs/environment/) | **yes, the initial setup script, then snapshot.** | snapshot freshness vs `main` is **unconfirmed** (docs say the snapshot is used for future tasks; rebuild trigger is not spelled out beyond re-running setup). |
| **grok bot** | A shared computer can persist files across local runs, subject to storage limits and refresh or repair wipes of folders such as `dist`, `build`, and `.cache`. No documented Build snapshot for wake runs. Cursor cloud agents are unused. | A persistent `rco.db` on the shared computer could be reused across local runs (**unconfirmed** as a supported pattern). There is **no** documented pre-warm for webhook wakes. | The wake still pays the full persona and memory load even if a database is already on disk. See [mill / grok bot notes](#mill--grok-bot-notes). |
| **gemini CLI, aider, windsurf, cline, ChatGPT scheduled tasks** | Local (or chat) tools. No documented isolated-VM Build/snapshot for a repo cache. | Run `rco update` locally, or in whatever CI the repo already uses, and point the instruction file at the pack; aider can `--read` a generated pack. | disk persistence is just the developer's machine. |
| **LangGraph** | container start / checkpointer / store. A compiled graph loads once per container. | An app startup hook or image build step could run `rco update`. | fully custom; not a product convention. |

### mill / grok bot notes

These points are specific to how grok bot is used with the mill, and are not needed to pick an rco instruction file or a pre-warm hook on another platform:

- Other inputs besides a generic webhook include a schedule, connectors, messages from another bot, and group chat. A message from another bot can start a run immediately.
- A disabled or paused routine has been observed to return HTTP 400; the app does not redeliver. Whether the sender retries is **unconfirmed**; the mill is believed not to redeliver.
- Cursor cloud agents are available but unused, mainly because of the cold-start cost of learning a repo. That is the cost rco is meant to cut; card 1313 is where a measured test belongs.
- Storage for transcripts, memory, and routines is off the shared computer (exact location, retention, and size limits are unconfirmed). The shared computer is where storage and file-count limits apply.

## 4. where products are similar, where they differ, and what addresses rco / cost pain

Several products share an expensive shape: a trigger starts a **fresh** run, the run loads standing instructions and some memory, and it does **not** automatically inherit the human's live chat. The claude scheduled tasks ("doesn't reuse sessions across events"), codex ("instruction chain once per run"), devin sessions (fresh snapshot copy; automations skip personal memory), and Copilot issue assignment (snapshot of the issue at start) all look like that. Where they differ is control. The devin product can **filter or dedup before** a full session (preflight script `id`s, or message an existing session instead of starting one), and claude/ChatGPT at least let you filter events or reuse a chat for scheduled tasks; grok bot today still pays a full persona and memory load per triggered event. The compaction and token cost are much more visible in claude code (`/usage`, `/context`, PreCompact hooks, logged `preTokens`) and partly in codex (`/compact`, `/status`, configurable thresholds) than in grok bot, where compaction is lossy and uninspectable and cost is not per wake; devin exposes per-session ACUs rather than tokens. For rco's cold-start problem, the closest product pattern is a **Build/snapshot/install script** that writes a cache to disk before the agent starts: cursor `install` on a Build, devin snapshots, jules initial setup snapshots, claude's cached setup script, and codex published-environment install scripts can all run `rco update`, while Copilot's `copilot-setup-steps.yml` can do it per Actions session. No platform shares one live `rco.db` across isolated VMs; the pack or snapshot will lag `main` until the next build, which is the trade to measure on card 1313.
